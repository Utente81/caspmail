# CasperMail Enterprise Architecture

This document outlines the technical design, security model, and infrastructure topologies of the CasperMail Enterprise Suite. It is intended for DevOps Engineers, Security Architects, and CISOs evaluating the platform.

## 1. Cloud-Native Kubernetes Topology

CasperMail relies on modern Kubernetes primitives to ensure absolute resilience and scalability. The entire stack is deployed declaratively using **ArgoCD** (GitOps).

### Ingress Layer (Traefik)
- **TLS Termination**: Strict TLS 1.2+ enforcement.
- **Security Headers**: Middleware injects strict `Content-Security-Policy` (CSP), HSTS (31536000 seconds), and anti-XSS headers.
- **Routing**: API paths (`/api/*`) are intelligently routed to the Fastify backend, while standard routes hit the React SPA. The `/admin` and `/realms` routes are safely forwarded to Keycloak.

### Compute Layer
- **Backend (Fastify)**: Stateless Node.js APIs utilizing connection pooling. Horizontally scalable via Kubernetes HPA (Horizontal Pod Autoscaler) based on CPU/Memory thresholds.
- **Frontend (React)**: Statically built SPA served via highly optimized containers. Divided into context boundaries (Login, Mail, SOC, Admin) to ensure zero-code leakage between isolated portals.

## 2. Zero-Trust Security & Identity

### HashiCorp Vault (KMS)
Vault acts as the central brain for all cryptographic operations and secrets management.
- **High Availability**: Configured in HA mode with integrated Raft storage backend.
- **Dynamic Secrets**: The Node.js backend does not possess static database credentials. Instead, it leases short-lived credentials generated by Vault. If a pod is compromised, the lease expires or can be instantly revoked.
- **Transit Engine**: Critical payload encryption utilizes Vault's Transit Secret Engine for "Encryption-as-a-Service", ensuring keys never leave the KMS memory boundaries.

### Keycloak (Identity Provider)
- **WebAuthn (Passkeys)**: Built-in support for biometric authentication (FIDO2, Windows Hello, Face ID). The default browser flow forces WebAuthn or Username/Password fallback, eliminating brute-force vulnerabilities.
- **Tokens**: The application utilizes standard OIDC PKCE flows for secure frontend integration. Access tokens (JWT) have short lifespans, while Refresh Tokens are strictly bound.

## 3. Data Persistence & High Availability

### CloudNativePG (PostgreSQL)
- **Clustering**: A highly available PostgreSQL cluster managed by the CloudNativePG operator.
- **Continuous Archiving**: WAL (Write-Ahead Logs) are continuously shipped to a MinIO (S3-compatible) object storage bucket.
- **Disaster Recovery**: Supports Point-In-Time-Recovery (PITR).

## 4. Security Operations Center (SOC) & SIEM

- **Real-Time Telemetry**: Security events generated by the Backend (or caught by the Client-Side DLP) are persisted in PostgreSQL and instantly broadcasted to active SOC dashboards via Server-Sent Events (SSE).
- **Asynchronous SIEM Export**: A dedicated queue handles the asynchronous transmission of `high` and `critical` severity events to third-party SIEM endpoints (Splunk, QRadar, Elastic) configured by Tenant Administrators via the frontend UI.
- **Webhook Delivery**: Payloads are formatted dynamically (JSON/CEF) based on tenant configuration, ensuring native ingestion across diverse enterprise ecosystems.

## 5. Observability (PLG Stack)

- **Loki & Promtail**: DaemonSet Promtail instances scrape all container stdout/stderr streams. Logs are aggregated in Grafana Loki for ultra-fast, label-based querying without heavy indexing overhead.
- **Grafana Dashboards**: Centralized dashboards provide deep insights into Keycloak login failures, Vault sealing status, Fastify API latency, and PostgreSQL replication lag.
